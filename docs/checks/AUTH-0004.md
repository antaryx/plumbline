# AUTH-0004 — PAM does not accept an empty password

| Field | Value |
|---|---|
| **ID** | `AUTH-0004` |
| **Module** | AUTH |
| **Base severity** | HIGH |
| **Tags** | auth, pam, credentials, empty-password |
| **Facts required** | `auth.pam` |
| **Since catalog** | 10 |
| **Platforms** | Linux, PAM hosts only |

## 1. What is tested

No `pam_unix.so` rule in any **auth** stack carries `nullok` or `nullok_secure`.

## 2. What `nullok` does

If the account's password field in `/etc/shadow` is empty, authenticate anyway.

Without it, an empty field is a **refusal** — the account simply cannot log in
with a password. With it, the empty field becomes a valid credential that
anybody can supply.

## 3. Two halves, introduced by different people

USERS-0003 reports accounts whose password field is empty. This check reports
whether PAM would accept one. **Neither is a login on its own; together they are
an unauthenticated shell** — and they are usually introduced separately: an
installer that ships `nullok` in the default stack, and an account created by a
script that never set a password.

It is worth checking even where no account currently has an empty field. The
PAM configuration is the durable half: the next account created without a
password is immediately usable by anyone who knows its name, with nothing to
notice at the moment it happens.

## 4. This is about empty passwords, not reversible storage

The two are sometimes conflated, because Windows policy has a "store passwords
using reversible encryption" setting and the phrase carries over.

Nothing in PAM stores a password reversibly. `pam_unix` hashes with `crypt(3)`,
and which algorithm it uses is **AUTH-0005**'s question. The Linux equivalent
of the reversible-storage risk is a weak hash, not this check. This one is
narrower and, on a host that has it, worse: no credential at all rather than a
cheap one.

`nullok_secure` is Debian's variant — an empty password is accepted, but only
from a terminal listed in `/etc/securetty`. Narrower, still an account that
authenticates with nothing, and the finding names the distinction because the
remediation urgency differs.

## 5. Every stack is searched, not only the shared one

`nullok` on `/etc/pam.d/login` admits an empty password exactly as `nullok` in
`system-auth` does. A host that has diverged from the shared stack has usually
diverged precisely there, so this check reads every service file the collector
resolved rather than the primary pair.

## 6. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | no auth rule carries a nullok argument | — | that an empty password field is refused rather than admitted |
| FAIL | one or more do | HIGH | **each file and line**, the link to USERS-0003, and — if present — what `nullok_secure` narrows |
| NOT_APPLICABLE | no `/etc/pam.d` | — | that another mechanism authenticates here |
| UNKNOWN | `/etc/pam.d` unreadable | `insufficient_privileges` | that every policy this host has is written there |
| UNKNOWN | an include could not be followed | `ambiguous_system_state` | which include |

The PASS rests on absence and is wrapped; the FAIL is an argument we read and
is not (ADR-0014).

## 7. Where this check cannot know

- **whether any account actually has an empty password.** USERS-0003 answers
  that. This check is about what happens when one does
- **`nullok` in the `password` stack.** There it means something different —
  allow a password to be *set* over an empty one — and is not a login. Only the
  auth stack is tested
- **other modules that accept empty credentials.** `pam_permit.so` in an auth
  stack authenticates everybody unconditionally, which is worse and is not
  covered here
- **whether `/etc/securetty` is restrictive**, which is what bounds
  `nullok_secure`

## 8. Known false positives

An appliance or embedded image where a console account with no password is the
intended recovery path. Enumerate before changing anything; suppress with the
reasoning recorded if that is genuinely the design.

## 9. Remediation

| | |
|---|---|
| Summary | Remove `nullok` from every `pam_unix.so` auth rule, and check the accounts relying on it. |
| Effort | LOW |
| Steps | **Find the accounts first** — `awk -F: '($2 == "") {print $1}' /etc/shadow`; decide per account whether to lock it or give it a password; remove the argument via `authselect disable-feature with-nullok` or `pam-auth-update`; **check the per-service stacks too**, since a diverged host has usually diverged there; confirm the accounts you kept can still log in, from a second session |
| Commands | `grep -rn 'nullok' /etc/pam.d/`, `awk -F: '($2 == "") {print $1}' /etc/shadow` |
| **Caution** | **Required.** Removing `nullok` immediately stops every empty-password account authenticating. On an appliance that is how the console account works — enumerate them first, and keep a session open in case one was yours. |
