# CRON-0001 — The system crontab is owned by root and writable only by root

| Field | Value |
|---|---|
| **ID** | `CRON-0001` |
| **Module** | CRON |
| **Base severity** | HIGH |
| **Tags** | cron, scheduled-tasks, privilege-escalation, file-permissions |
| **Facts required** | `cron.files` |
| **Since catalog** | 7 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

`/etc/crontab` is owned by uid 0 and gid 0, and its mode grants write permission
to neither group nor other (`mode & 0022 == 0`).

## 2. Why it matters

`/etc/crontab` names commands and the accounts they run as, and cron executes
them without asking anything further. Write access to that file is write access
to a root shell that starts on a schedule — no exploit, no authentication step,
and nothing unusual-looking afterwards, because a crontab entry is what a
crontab is supposed to contain.

Two conditions produce it and they are the same exposure reached two ways. A
file owned by an unprivileged account is one that account can rewrite **and
chmod** at will, so ownership matters as much as the mode. A root-owned file
that is group- or world-writable is the same thing without the indirection.

Both arise from ordinary accidents far more often than from attack: a deployment
script that chowns `/etc` to a service account, a restored backup carrying the
wrong ownership, an administrator who ran `chmod -R` on a parent. That is
precisely why it is worth checking — nobody remembers doing it.

## 3. Source of truth

| | |
|---|---|
| Source | `stat(2)` on `/etc/crontab` — mode and owner only |
| Daemon default when unset | Not applicable; the file either exists or does not |
| Reference | `crontab(5)` |

The file's **contents are never read**. This check asks who may write the
schedule, not what it says; a crontab's command lines carry operator data and
frequently credentials, and collecting them for a check that does not read them
would put all of it into a bundle designed to travel.

## 4. Distribution variations

Every mainstream distribution ships `/etc/crontab` as `root:root` mode 0644.
That passes this check: 0644 is not writable by group or other. The
world-**readability** of the vendor default is CRON-0005's business, at LOW.

A host that schedules everything through `/etc/cron.d` may legitimately have no
`/etc/crontab` at all. That is NOT_APPLICABLE here, not a failure.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | root-owned and not group/other writable | — | the mode and owner observed |
| FAIL | owner is not uid 0 / gid 0 | HIGH | the uid and gid found, and that the account can also chmod it |
| FAIL | mode grants group or other write | HIGH | the octal mode |
| NOT_APPLICABLE | no system cron on this host | — | — |
| NOT_APPLICABLE | cron installed, `/etc/crontab` absent | — | that scheduling through `/etc/cron.d` is normal |
| UNKNOWN | the path could not be stat'ed | `insufficient_privileges` | that owner and mode are unknown |
| UNKNOWN | `/etc/crontab` is a symbolic link | `ambiguous_system_state` | that the link's metadata is not the target's |

The symlink case is not pedantry. `Stat` does not follow the link, so the mode
and owner recorded describe the link rather than the file cron reads through it
— and a symlink standing where `/etc/crontab` should be is exactly the
redirection an attacker installs. Reporting either verdict would be describing
the wrong inode.

## 6. Where this check cannot know

- **what the crontab contains.** A correctly-owned file full of malicious jobs
  passes. This check is about who may change it, not about what is in it
- **the target of a symlink.** The module does not follow links, so a redirected
  crontab is reported as unknowable rather than resolved
- **the permissions of the scripts the crontab calls.** A perfectly-owned
  crontab invoking a world-writable script in `/usr/local/bin` is a complete
  escalation this check cannot see — that needs the filesystem walker
- **per-user crontabs.** They live in a spool directory whose path differs by
  distribution (`/var/spool/cron/crontabs` on Debian-family, `/var/spool/cron`
  on Red Hat-family) and is unreadable unprivileged. Not collected in WP-19
- **whether the exposure was used.** A file that was writable yesterday and is
  correct today reports PASS

## 7. Known false positives

None known. A deliberately group-writable `/etc/crontab` is a decision to let a
non-root group schedule root jobs; the finding is correct about it and it should
be suppressed with that reasoning recorded, not excused.

## 8. Remediation

| | |
|---|---|
| Summary | Restore root ownership and remove group and other write permission. |
| Effort | LOW |
| Steps | **read the file before changing anything**; `chown root:root /etc/crontab` and `chmod 600`; find out how it happened — a wrong file beside a wrong `/etc/cron.d` means `chmod -R` or a restored backup; verify against the package with `dpkg --verify cron` or `rpm -V cronie`; no reload is needed |
| Commands | `stat -c '%n %a %U:%G' /etc/crontab`, `chown root:root /etc/crontab && chmod 600 /etc/crontab` |
| **Caution** | **Required.** Fix the permissions, but do not stop there. If a non-root account could write this file, the correct assumption is that the host is compromised rather than merely misconfigured — read the contents and the logs before you overwrite the evidence. |
