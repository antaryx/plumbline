# CRON-0003 — Access to crontab is restricted by an allow list

| Field | Value |
|---|---|
| **ID** | `CRON-0003` |
| **Module** | CRON |
| **Base severity** | MEDIUM |
| **Tags** | cron, scheduled-tasks, access-control, persistence |
| **Facts required** | `cron.files` |
| **Since catalog** | 7 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

`/etc/cron.allow` exists.

That is the whole proposition, and it is worth stating that narrowly because the
precedence between the two access-control files is what makes it correct.

## 2. The precedence, which is the substance of this check

The two files **do not combine**. `crontab(1)` defines three cases:

| Situation | Effect |
|---|---|
| `cron.allow` **exists** | Only the users named in it may use `crontab`. **`cron.deny` is ignored entirely** — not merged, not consulted |
| `cron.allow` absent, `cron.deny` exists | Every user **except** those named in `cron.deny` may use `crontab` |
| **Neither** exists | Decided by how the cron package was built, not by anything on the filesystem. Debian's `cron` and Red Hat's `cronie` choose differently and both document it as site-dependent |

Only the first is a determinate, allow-listed configuration, so only the first
passes.

**The direction is what matters.** An allow list fails **closed**: an account
created tomorrow is not on it and cannot schedule anything until somebody
decides it should. A deny list fails **open**: the same account is permitted by
omission, and nothing about creating it draws attention to the fact. Every
service account a package installs, every user a directory service introduces,
and every account an attacker adds is admitted by a deny list without a single
edit to it.

Scheduled jobs deserve this because they are the classic persistence mechanism:
a job survives reboots, runs without a session, and looks exactly like the
legitimate jobs beside it.

### Why case 3 is FAIL and not UNKNOWN

This is the one judgement in the module worth defending explicitly, because
CLAUDE.md rule 3 forbids guessing.

The proposition tested is *"cron access is restricted by an allow list"*. With
neither file present, that proposition is **decided**: no allow list exists.
What is unknowable is the *consequence* — whether the package then permits
everyone or only root — and the finding says so rather than pretending
otherwise. The verdict is definite; the blast radius is not, and the detail
states plainly that it "cannot even be bounded" from here. Returning UNKNOWN
would be reporting ignorance about something the filesystem answered.

## 3. Source of truth

| | |
|---|---|
| Source | existence of `/etc/cron.allow` and `/etc/cron.deny` |
| Daemon default when unset | Compile-time; see case 3 above |
| Reference | `crontab(1)` |

Neither file's **contents** are read, so an empty `cron.allow` — the strictest
configuration possible, permitting nobody but root — is indistinguishable here
from a populated one.

## 4. Distribution variations

Debian and Ubuntu ship neither file. RHEL and Fedora ship an empty
`/etc/cron.deny`, which permits every user. A stock host of any of them fails
this check, correctly, and by vendor default rather than by mistake.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `cron.allow` exists | — | that access fails closed |
| PASS | `cron.allow` and `cron.deny` both exist | — | **that `cron.deny` is being ignored** and should be removed |
| FAIL | `cron.allow` absent, `cron.deny` present | MEDIUM | that the deny list fails open and admits new accounts by omission |
| FAIL | neither exists | MEDIUM | that the outcome is a compile-time property and cannot be bounded from here |
| NOT_APPLICABLE | no system cron on this host | — | — |
| UNKNOWN | `cron.allow`'s existence could not be determined | `insufficient_privileges` | that its presence decides the whole mechanism |

The both-files-present case is a PASS that names a trap. cron ignores
`cron.deny` outright when `cron.allow` exists, so an administrator maintaining
it is editing a file with no effect while believing they have removed someone's
access — the same unreachable-configuration failure USERS-0005 reports for a
duplicated account name.

## 6. Where this check cannot know

- **who is on the list.** No contents are read, so an empty allow list and a
  list naming every account on the host are the same observation here
- **whether the names on it should be there.** That needs the list joined
  against `users.passwd` and against what those accounts are for
- **existing crontabs.** An account removed from the allow list keeps any
  crontab it already had — the job keeps running, the user simply cannot see or
  edit it any more. Enumerating the spool is not done in WP-19
- **`at` access**, governed by the separate `/etc/at.allow` and `/etc/at.deny`,
  which this module does not collect
- **systemd timers**, which are not governed by these files at all

## 7. Known false positives

A single-purpose host where every account is administrative has little to gain
from an allow list. The finding is still correct — the mechanism is absent — and
suppression with that reasoning recorded is the right response.

## 8. Remediation

| | |
|---|---|
| Summary | Create `/etc/cron.allow` listing the accounts that may schedule jobs, and remove `/etc/cron.deny`. |
| Effort | MEDIUM |
| Steps | **enumerate the spool first** (`/var/spool/cron/crontabs` on Debian-family, `/var/spool/cron` on Red Hat-family) so the list does not omit an account that already has a crontab; write the file; `chown root:root` and `chmod 600` it (CRON-0004 checks this); remove `cron.deny` once `cron.allow` is in place; verify from an unprivileged account that is not on the list |
| Commands | `ls -l /etc/cron.allow /etc/cron.deny`, `ls /var/spool/cron/crontabs /var/spool/cron 2>/dev/null` |
| **Caution** | **Required.** An allow list that omits an account which currently has a crontab does not delete that crontab — the job keeps running — but the account can no longer list or edit it, which turns a scheduled job into one nobody can see or change. Enumerate the spool before writing the file, not afterwards. |
