# CRON-0002 — The cron drop-in directories are owned by root and writable only by root

| Field | Value |
|---|---|
| **ID** | `CRON-0002` |
| **Module** | CRON |
| **Base severity** | HIGH |
| **Tags** | cron, scheduled-tasks, privilege-escalation, file-permissions |
| **Facts required** | `cron.files` |
| **Since catalog** | 7 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

Each of `/etc/cron.d`, `/etc/cron.hourly`, `/etc/cron.daily`, `/etc/cron.weekly`
and `/etc/cron.monthly` that exists is a directory, is owned by uid 0 / gid 0,
and grants write permission to neither group nor other.

## 2. Why it matters

cron runs whatever it finds in these directories, as root unless the file says
otherwise. Write access to any one of them is enough to schedule arbitrary code
as root — and the attacker does not need to modify an existing file, only to
**create** one. That leaves every existing file byte-identical, so package
verification and file-integrity monitoring that watch known paths report nothing
wrong.

`/etc/cron.d` is the sharper shape, because its files carry a user field: a file
dropped there can name root explicitly regardless of who wrote it.

The directory's own mode is what matters, not the modes of the files inside it.
Unix permits creating a file in any directory you can write, whoever owns the
existing contents — so a world-writable `/etc/cron.d` full of correctly-owned
root files is still a root shell for anyone with an account.

## 4. Distribution variations

Not every distribution ships all five. Absent directories are not a finding —
cron cannot run anything from a directory that is not there — and if none of
them exists the check is NOT_APPLICABLE.

All mainstream distributions ship the ones they do have as `root:root` mode
0755, which passes. The world-readability is CRON-0005's business at LOW.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | every directory present is root-owned and not group/other writable | — | how many were examined, and which |
| FAIL | a directory's owner is not uid 0 / gid 0 | HIGH | the path, the uid and gid |
| FAIL | a directory's mode grants group or other write | HIGH | the path and the octal mode |
| FAIL | a drop-in path is not a directory | HIGH | that it is a symlink, and that links are not followed |
| NOT_APPLICABLE | no system cron, or none of the five exists | — | — |
| UNKNOWN | no violation found but a path could not be stat'ed | `insufficient_privileges` | which paths were unknowable |

All five are reported in **one** finding rather than one per directory. They are
a single control — cron executes from all of them identically, and an operator
who fixes one and leaves another has not reduced the exposure at all — so
splitting them would produce findings that look independently actionable and are
not.

## 6. Where this check cannot know

- **the files inside.** A correctly-owned directory containing a job that calls
  a world-writable script is a complete escalation this check cannot see
- **the target of a symlinked directory**, for the same reason as CRON-0001
- **`/etc/cron.d` files' user fields.** Which account a dropped file names is a
  content question, and no content is collected
- **systemd timers**, which schedule work on most modern hosts and are not cron
  at all. A host that has migrated to them entirely can pass every check in this
  module while scheduling everything through a mechanism it never examined

## 7. Known false positives

A deployment directory deliberately group-writable so a CI account may drop
jobs. That is a real grant of root scheduling to that group; suppress it with
the reasoning recorded.

## 8. Remediation

| | |
|---|---|
| Summary | Restore root ownership and remove group and other write permission from every cron directory. |
| Effort | LOW |
| Steps | list the contents first and **look for files you did not put there**; `chown root:root /etc/cron.*` then `chmod 755` (or 700 to also close CRON-0005); check the files inside as well as the directory; establish how it happened, since a script that chowned one parent has probably done it elsewhere |
| Commands | `stat -c '%n %a %U:%G' /etc/cron.d /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly`, `find /etc/cron.d -type f ! -user root` |
| **Caution** | **Required.** Treat a writable cron directory as a compromise until shown otherwise. Unlike a modified file, a dropped-in file leaves the rest of the directory byte-identical, so package verification and file-integrity monitoring that only watch known paths will report nothing wrong. |
