# CRON-0005 — The cron schedule is not readable by unprivileged accounts

| Field | Value |
|---|---|
| **ID** | `CRON-0005` |
| **Module** | CRON |
| **Base severity** | LOW |
| **Tags** | cron, scheduled-tasks, information-disclosure |
| **Facts required** | `cron.files` |
| **Since catalog** | 7 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

`/etc/crontab` and each cron drop-in directory that exists grants read
permission to neither group nor other (`mode & 0044 == 0`).

## 2. Why it matters — and why it is LOW

The schedule is reconnaissance. It names what runs as root, where the scripts
live, and — precisely — **when**. That last part is what makes it worth
restricting: an attacker who knows a backup script runs as root at 03:15 and
reads from a directory their account can write knows exactly which file to place
and exactly how long they will wait. Without the schedule they are guessing at
both.

Argument lists are frequently worse than the timing. Cron lines routinely carry
database names, hostnames, API endpoints and occasionally credentials passed on
the command line, all of which a world-readable crontab hands to anyone with a
shell.

**This is a disclosure control, not an escalation one, and the severity says
so.** CRON-0001 and CRON-0002 cover who may *write* the schedule, which is the
exposure that matters; this check covers who may read it. The CIS Benchmarks
require 0600 on `/etc/crontab` and 0700 on the drop-in directories; Debian,
Ubuntu, RHEL and Fedora all ship 0644 and 0755. **A host that has never been
hardened fails this by vendor default rather than by mistake**, which is exactly
why reporting it at the same weight as a world-writable `/etc/cron.d` would be
wrong — it would teach the reader to skim past both.

## 4. Distribution variations

Universal. Every mainstream distribution ships `/etc/crontab` at 0644 and the
drop-in directories at 0755, so this check fails on a stock install of all of
them. `cron-vendor` is the fixture that pins that.

The access-control files are deliberately **not** included here: knowing who may
schedule jobs is not itself a disclosure, and CRON-0004 covers the property of
those files that matters.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | every path present is readable only by root | — | which paths were examined |
| FAIL | any path grants group or other read | LOW | each path and its octal mode, that this is disclosure rather than escalation, and that these are vendor defaults |
| NOT_APPLICABLE | no system cron, or neither the crontab nor any drop-in directory exists | — | — |
| UNKNOWN | no violation found but a path could not be stat'ed | `insufficient_privileges` | which paths were unknowable |

## 6. Where this check cannot know

- **whether the host has untrusted local accounts at all.** On a single-user
  machine this control protects nothing, and the finding cannot tell
- **what the lines actually contain.** No contents are read, so a schedule
  disclosing a credential and one disclosing nothing interesting are the same
  observation here
- **`ps` visibility.** A credential passed as a command-line argument is visible
  to every user on the host through `/proc` **whatever this file's mode is**.
  Tightening the mode does not fix that one, and the remediation says so —
  moving the secret into a root-only environment file does
- **the modes of files inside the directories**, only the directories themselves

## 7. Known false positives

Monitoring and configuration-management agents that inventory scheduled jobs as
a non-root user need read access. Tightening the mode makes them silently report
nothing rather than fail loudly, which is worse than the disclosure on many
hosts. A single-user machine has no local attacker for this to defend against at
all. Both are legitimate suppressions with the reasoning recorded.

## 8. Remediation

| | |
|---|---|
| Summary | Remove group and other read permission from the crontab and the drop-in directories. |
| Effort | LOW |
| Steps | **decide whether this applies to you first** — on a host with no untrusted accounts it protects nothing; `chmod 600 /etc/crontab`; `chmod 700` the five directories; check what read them; while there, look at whether any line passes a secret as an argument, because `ps` discloses that regardless of this mode |
| Commands | `stat -c '%n %a %U:%G' /etc/crontab /etc/cron.d /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly` |
| **Caution** | **Required.** `run-parts` needs no read access for anyone but root, so cron itself is unaffected — but monitoring and configuration-management agents that inventory scheduled jobs as a non-root user will silently start reporting nothing rather than failing loudly. Check what reads these paths before tightening them. |
