# SSHD-0012 — No deprecated key exchange method is offered

| Field | Value |
|---|---|
| **ID** | `SSHD-0012` |
| **Module** | SSHD |
| **Base severity** | HIGH |
| **Tags** | ssh, cryptography, remote-access |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

`KexAlgorithms` is set to an explicit list containing none of the methods below.

## 2. Why it matters

Key exchange establishes the shared secret everything else in the session depends
on. It is the one negotiation where a weakness is not partial: an adversary who
recovers the exchanged secret **reads and modifies the session regardless of how
strong the cipher and MAC were**.

| Family | Why |
|---|---|
| **1024-bit MODP groups** (`*group1-*`) | Logjam (2015) showed that one expensive precomputation against a fixed 1024-bit group makes individual exchanges cheap thereafter, and that the small number of groups in widespread use makes that precomputation worth doing. The prudent assumption is that it has been done |
| **SHA-1 key exchanges** (`*sha1*`) | RFC 9142 deprecates SHA-1 for SSH key exchange; OpenSSH removed these from its defaults in 8.2 |
| **`rsa1024-*`** | Below every current minimum |

`none` fails for the obvious reason.

**Out of scope: Terrapin (CVE-2023-48795).** That is a weakness in the
handshake's sequence-number handling rather than in any algorithm on this list,
and it is fixed by OpenSSH 9.6's strict-KEX extension rather than by a
configuration change. A host with a perfectly acceptable `KexAlgorithms` list can
still be vulnerable if the binary predates 9.6. Version-based detection belongs
to a vulnerability feed, not to this check.

## 4. Distribution variations

As SSHD-0010 and SSHD-0011: RHEL 8+ and Fedora govern this through
`crypto-policies`, and the `LEGACY` profile re-enables SHA-1 exchanges.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|

| FAIL | explicit list containing a weak entry | HIGH | each weak entry and why |

| UNKNOWN | keyword absent, or a relative form adding nothing weak, or a `-` form | `ambiguous_system_state` | which case, and why it cannot be resolved |
| UNKNOWN | value unparseable as a list | `unparseable_source` | — |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **the built-in default list.** This is the whole reason an absent keyword is
  UNKNOWN rather than PASS. The effective list is compiled into the sshd binary;
  it changed between OpenSSH releases, and Red Hat's `crypto-policies` rewrites
  it at build and at runtime. Plumbline does not read the binary's version —
  that needs `sshd -T`, an `Exec` through the seam, deferred by BUILD-RUNBOOK
  WP-18. Reporting PASS would assert the contents of a list never read
- **the relative forms.** `+`, `-` and `^` all modify the built-in list, so they
  inherit the same unknowability — with one asymmetry: a `+` or `^` that **adds**
  a broken method is a definite FAIL, because that method is enabled whatever the
  rest holds. Same asymmetry as ADR-0014, reached independently
- **`/etc/ssh/moduli`.** Where `diffie-hellman-group-exchange-*` is offered, the
  actual group size comes from that file, and 1024-bit moduli left in it undo
  much of the point of a good list. Plumbline does not read it
- **the sshd version**, so Terrapin is not detected — see §2
- **`update-crypto-policies`** on RHEL-family hosts

## 7. Known false positives

The same client-compatibility case as SSHD-0010, and more acute here: key
exchange is the *first* thing negotiated, so an incompatible client fails before
authentication with an error naming nothing on this host.

## 8. Remediation

| | |
|---|---|
| Summary | Set an explicit `KexAlgorithms` list of SHA-2 curve and large-group methods. |
| Effort | MEDIUM |
| Steps | set `KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org,diffie-hellman-group16-sha512,diffie-hellman-group-exchange-sha256`; **also strip moduli below 3071 bits from `/etc/ssh/moduli`**; confirm the binary is 9.6+ for the Terrapin mitigation; check `update-crypto-policies --show`; reload |
| Commands | `sshd -T \| grep -i '^kexalgorithms'`, `ssh -Q kex` |
| **Caution** | **Required.** This is the algorithm list most likely to break old automation. A client supporting nothing on the list fails before authentication with "no matching key exchange method found" and no indication of which host setting caused it. Check every client that reaches this host, including backup agents and monitoring probes. |
