# SSHD-0019 — sshd verifies ownership and permissions of user key files

| Field | Value |
|---|---|
| **ID** | `SSHD-0019` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, authentication, file-permissions |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `StrictModes` is `yes`.

## 2. Why it matters

Before accepting a public key, sshd checks that the user owns their home
directory, `~/.ssh` and `~/.ssh/authorized_keys`, and that none of them is
writable by group or other. `StrictModes yes` is what performs that check.

With `StrictModes no`, a world-writable home directory becomes a way in: anyone
who can write it creates `~/.ssh/authorized_keys`, adds their own public key, and
logs in as that user. No credential is stolen and nothing is guessed — the account
simply starts trusting a new key. The same applies to a home directory on a
group-writable share, which is the more common accidental case.

The reason this setting gets turned off is almost always a home directory on a
network filesystem whose ownership does not survive the mount, and **the correct
fix is to repair the mount rather than to stop checking**.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `yes`, or absent (the default is secure) | — | that a key file writable by others is refused |
| FAIL | `no` | MEDIUM | that anyone able to write a home directory can add a key |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether any home directory is actually writable.** That is the question that
  decides whether this setting is currently protecting anything, and it needs
  filesystem facts this check does not have. A FAIL says the guard is off, not
  that it was needed
- **`AuthorizedKeysFile`**, which can point somewhere outside the home directory
  entirely and change what `StrictModes` is guarding
- **whether an unexpected key is already in an `authorized_keys` file**, which is
  what a host that has been running with `StrictModes no` most needs checked

## 7. Known false positives

None. A host with NFS home directories has a real operational problem, but
disabling the check is a workaround rather than a solution, and the finding
correctly says so.

## 8. Remediation

| | |
|---|---|
| Summary | Set `StrictModes yes` and fix the permissions that made turning it off seem necessary. |
| Effort | LOW |
| Steps | find what would now be rejected with `find /home -maxdepth 1 -perm /022 -type d`; repair ownership and modes; for NFS, fix the export or the idmap rather than the sshd setting; set the keyword; reload |
| Commands | `sshd -T \| grep -i strictmodes`, `find /home -maxdepth 1 -perm /022 -type d` |
| **Caution** | **Required.** Turning this back on refuses key authentication for any user whose permissions are currently wrong, and the failure is **silent from the client's side** — it falls through to the next method or is rejected. Audit and repair the directories in the same maintenance window. |
