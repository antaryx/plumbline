# SSHD-0014 — Host-based authentication is disabled

| Field | Value |
|---|---|
| **ID** | `SSHD-0014` |
| **Module** | SSHD |
| **Base severity** | HIGH |
| **Tags** | ssh, remote-access, authentication, lateral-movement |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `HostbasedAuthentication` is `no`.

## 2. Why it matters

Host-based authentication admits a user because of the **machine** they are
connecting from, not because of anything they know or hold. The client host
proves its identity with its own host key, and from there sshd accepts whichever
local username the client asserts.

The trusted host's security boundary therefore becomes this host's security
boundary. Anyone with root on the trusted machine — or anyone who can read its
host key, which lives on disk and is often included in backups and machine
images — can authenticate here as any user the trust covers. A single compromised
workstation becomes access to every host that trusted it, with no credential to
steal and nothing in this host's logs to distinguish it from a legitimate login.

## 4. Distribution variations

None. Every distribution leaves the default or sets `no`.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `no`, or absent (the default is secure) | — | that a credential is required rather than a machine |
| FAIL | `yes` | HIGH | the host-key exposure |
| FAIL | `no` globally, `yes` inside a Match block | MEDIUM | the Match criteria, quoted |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **which hosts are trusted.** `/etc/ssh/shosts.equiv`, `/etc/hosts.equiv` and
  per-user `~/.shosts` hold the list, and none of them is read here. A FAIL says
  the mechanism is enabled, not how far the trust reaches
- **`HostbasedUsesNameFromPacketOnly`**, which makes the trust even weaker by
  believing the name the client sends
- **whether the trusted hosts' keys have leaked**, which is the actual question
  and is not answerable from any single host

## 7. Known false positives

HPC clusters, parallel shells and older batch schedulers depend on this. Each of
those is currently authenticating with no per-user credential; the finding is
correct, and the answer is migration to keys with forced commands rather than
suppression.

## 8. Remediation

| | |
|---|---|
| Summary | Set `HostbasedAuthentication no` and remove the trust configuration behind it. |
| Effort | MEDIUM |
| Steps | list what depends on it from `shosts.equiv`/`hosts.equiv`/`~/.shosts`; replace with per-account keys and forced commands; set the keyword; remove the trust files after recording their contents; reload |
| Commands | `sshd -T \| grep -i hostbasedauthentication`, `cat /etc/ssh/shosts.equiv /etc/hosts.equiv 2>/dev/null` |
| **Caution** | **Required.** Cluster tooling from the HPC and older Unix worlds depends on this. Migrate to keys rather than leaving the trust in place, and expect the migration to take longer than the config change. |
