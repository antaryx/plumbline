# SSHD-0020 — sshd runs the PAM account and session stack

| Field | Value |
|---|---|
| **ID** | `SSHD-0020` |
| **Module** | SSHD |
| **Base severity** | HIGH |
| **Tags** | ssh, remote-access, authentication, policy-enforcement |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `UsePAM` is `yes`.

## 2. Why it matters

**This is the joint between the SSHD module and the USERS module.** With
`UsePAM no`, sshd authenticates against `/etc/shadow` itself and starts the
session directly. Nothing in the PAM stack runs, and everything that lives there
stops applying to SSH logins:

| What is lost | Where it was configured |
|---|---|
| Account expiry and password aging | `pam_unix` account phase — the shadow fields **USERS-0009 and USERS-0010** report |
| Lockout after repeated failures | `pam_faillock`, `pam_tally2` |
| Access restrictions, including `/etc/nologin` | `pam_access`, `pam_time`, `pam_nologin` |
| Session accounting and limits | `pam_limits`, `pam_loginuid` |

The policy is configured and simply not applied. That is worse than an absent
policy, because the operator believes it is in force and the audit that checked
`/etc/shadow` agrees with them.

## 4. Distribution variations

Every mainstream distribution ships `UsePAM yes` in its packaged `sshd_config`,
precisely because the upstream default is `no`. A host failing this has either
had the line removed or is running a configuration built from scratch — a
container image or an appliance, most often.

**Not permitted inside a `Match` block.**

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `yes` | — | that account expiry, lockout and access policy apply |
| FAIL | `no` | HIGH | which policies are bypassed, by name |
| FAIL | absent | HIGH | that the built-in default is `no` |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether `/etc/pam.d/sshd` exists or is sane.** Enabling `UsePAM` without it
  refuses every login, so the remediation checks for the file first. Reading the
  PAM stack is the AUTH module's work (WP-24)
- **what the PAM stack would enforce.** A host with `UsePAM yes` and an empty PAM
  configuration is no better off, and this check cannot tell the difference
- **the `PasswordAuthentication` interaction.** With `UsePAM yes`, PAM can accept
  a password through keyboard-interactive even when SSHD-0003 passes; the two
  checks are individually correct and jointly incomplete until
  `KbdInteractiveAuthentication` is read

## 7. Known false positives

A minimal container running sshd with no PAM libraries installed cannot set this
and would break if it did. That is a real constraint, and the correct response is
to record it — such an image is also not enforcing any of the policy in §2.

## 8. Remediation

| | |
|---|---|
| Summary | Set `UsePAM yes` and confirm the PAM stack for sshd is present. |
| Effort | LOW |
| Steps | **confirm `/etc/pam.d/sshd` exists before enabling**; set the keyword; reload from a session you are not depending on; verify an expired password is now prompted for; note the `KbdInteractiveAuthentication` interaction with SSHD-0003 |
| Commands | `sshd -T \| grep -i usepam`, `ls -l /etc/pam.d/sshd` |
| **Caution** | **Required.** If `/etc/pam.d/sshd` is missing or broken, turning `UsePAM` on refuses **every** SSH login immediately. Verify the file exists, reload from a session you are not depending on, and keep a console or second session open. |
