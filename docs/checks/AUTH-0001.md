# AUTH-0001 — A password quality module is enforced

| Field | Value |
|---|---|
| **ID** | `AUTH-0001` |
| **Module** | AUTH |
| **Base severity** | HIGH |
| **Tags** | auth, pam, password, credentials |
| **Facts required** | `auth.pam` |
| **Since catalog** | 10 |
| **Platforms** | Linux, PAM hosts only |

## 1. What is tested

`pam_pwquality.so` or `pam_cracklib.so` appears in the **password** stack with
an **enforcing** control.

## 2. Nothing checks a password by default

Without a quality module, `passwd` accepts anything a user types: their own
username, one character, the empty string where PAM allows it. The absence is
silent — no warning at install time, nothing in the logs — so a password policy
document describing fourteen-character minimums can coexist indefinitely with a
host that enforces none of it.

## 3. The control is the half most often wrong

PAM's `optional` means the result is **ignored entirely**. The module runs, it
computes that the password is unacceptable, and PAM sets it anyway.

```
password optional pam_pwquality.so retry=3      # does nothing
password requisite pam_pwquality.so retry=3     # refuses the password
```

Those two lines read identically to a human skimming a stack, produce no
distinguishing output, and differ completely in effect. That is why this check
tests the control rather than the presence, and why `auth-optional` exists as a
fixture of its own.

| Control | Enforcing | Why |
|---|---|---|
| `required` | yes | failure fails the stack, after running the rest |
| `requisite` | yes | failure fails the stack immediately |
| `optional` | **no** | result ignored unless it is the only module |
| `sufficient` | no | success short-circuits; failure is ignored |
| `[... default=die]` | yes | failure ends the stack |
| `[... default=bad]` | yes | failure is recorded as failure |
| `[... default=ignore]` | **no** | failure is discarded |
| any other bracketed form | **treated as not enforcing** | see below |

A bracketed control this code does not recognise is reported as *not*
enforcing. That is the conservative direction: it produces a finding a human
reads, rather than a PASS drawn from a control expression nothing understood.

## 4. Two module names

`pam_cracklib.so` is the older module; `pam_pwquality.so` replaced it and reads
`/etc/security/pwquality.conf`. Long-lived hosts still have the first. Checking
only for the current name would report "no quality enforcement" on a host that
has it — a wrong verdict produced by the module having been renamed.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | a quality module is present with an enforcing control | — | the module, the control, and that its parameters are AUTH-0002's question |
| FAIL | present but not enforcing | HIGH | **that PAM ignores the result entirely** and that the line reads like a working one |
| FAIL | absent from the password stack | HIGH | that `passwd` accepts any string, and that nothing logs it |
| NOT_APPLICABLE | no `/etc/pam.d` | — | that another mechanism authenticates here |
| UNKNOWN | `/etc/pam.d` unreadable | `insufficient_privileges` | that every policy this host has is written there |
| UNKNOWN | PAM present, no recognised shared stack | `ambiguous_system_state` | that guessing at the layout would read as a clean host |
| UNKNOWN | an include could not be followed | `ambiguous_system_state` | which include, and that the stack examined is not the stack in force |

The two PASS-adjacent paths are unguarded: an enforcing rule we read is a fact.
The absent-FAIL rests on absence and is wrapped (ADR-0014).

## 6. Where this check cannot know

- **the surrounding control flow.** A `sufficient` rule placed above the
  quality module short-circuits the stack before reaching it, and this check
  does not detect that. Simulating PAM means implementing the bracketed jump
  semantics correctly, and a stack simulator that is subtly wrong produces
  confident verdicts about which module runs — worse than not having one
- **whether the module is installed.** A rule marked `-password` (leading
  hyphen) tells PAM not to log when the module is missing, so it can be present
  in the file and absent from the host. The fact records `Optional` for this;
  no check acts on it yet
- **per-service divergence.** Only the shared stacks are examined. A service
  with its own password rules is not covered
- **what the rules actually require.** AUTH-0002

## 7. Known false positives

A host where password setting is delegated entirely to a directory service and
the local stack is vestigial. The observation stays correct — local `passwd`
enforces nothing — and suppression with that reasoning is right.

## 8. Remediation

| | |
|---|---|
| Summary | Add `pam_pwquality.so` to the password stack with an enforcing control. |
| Effort | MEDIUM |
| Steps | Install the module if missing; **do not hand-edit a generated stack** — `authselect` owns Red Hat's `system-auth` and overwrites hand edits silently, `pam-auth-update` owns Debian's `common-password`; place the rule **before** `pam_unix.so`, because after it the password is already set; put the parameters in `/etc/security/pwquality.conf` rather than as module arguments; test from a second session with a one-character password |
| Commands | `grep -E 'pam_pwquality|pam_cracklib' /etc/pam.d/*`, `authselect current`, `passwd testuser` |
| **Caution** | **Required.** A wrong PAM edit can lock every account out including root, and the failure appears at the next authentication rather than when the file is saved. Keep a root session open, test with a second login before closing it. |
