# AUTH-0003 — Repeated authentication failures lock the account

| Field | Value |
|---|---|
| **ID** | `AUTH-0003` |
| **Module** | AUTH |
| **Base severity** | MEDIUM |
| **Tags** | auth, pam, brute-force, lockout |
| **Facts required** | `auth.pam` |
| **Since catalog** | 10 |
| **Platforms** | Linux, PAM hosts only |

## 1. What is tested

`pam_faillock.so`, `pam_tally2.so` or `pam_tally.so` appears in the **auth**
stack.

## 2. Quality and lockout are two halves of one control

Password quality sets the size of the search space. Lockout sets how much of it
an attacker may search. Neither is sufficient alone, and the second is the
cheaper to add, because it costs users nothing until they mistype.

It matters most **where nobody is watching**. sshd counts its own failures per
connection and gives up, which makes remote brute force expensive but not
impossible. `su`, `sudo`, console `login`, and any service authenticating
through PAM without its own limiter have no such counter. A lockout module is
the only thing between a stolen shell and an unlimited number of guesses at the
next account.

## 3. Three module names

`pam_faillock` is current. `pam_tally2` is deprecated and removed in recent
releases but is what a long-lived host has; `pam_tally` is older still.
Checking only for the current one would report "no lockout is configured" on a
host that has one.

## 4. Thresholds are reported, not judged

Where `deny` and `unlock_time` can be read — from the module arguments or from
`/etc/security/faillock.conf`, resolved in that precedence — the finding quotes
them. It does not fail on the numbers.

Whether five failures or ten is right depends on who uses the host and how they
reach it, and a verdict on the number would fire on defensible configurations
far more often than on dangerous ones. The one case the detail calls out is
`unlock_time = 0`: a permanent lock turns a guessing attempt into a denial of
service that anybody who knows a username can trigger, repeatedly, with an
administrator needed for every recovery.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | a counter is in the auth stack | — | the module, and the thresholds where readable — **including that `unlock_time = 0` is self-inflicted DoS surface** |
| FAIL | no counter in the auth stack | MEDIUM | **that sshd's own limiter does not cover `su`, `sudo` or console login** |
| NOT_APPLICABLE | no `/etc/pam.d` | — | that another mechanism authenticates here |
| UNKNOWN | `/etc/pam.d` unreadable | `insufficient_privileges` | that every policy this host has is written there |
| UNKNOWN | an include could not be followed | `ambiguous_system_state` | which include |

## 6. Where this check cannot know

- **whether the `account` stack has its rule too.** faillock needs `auth
  preauth`, `auth authfail` **and** `account required` to work fully; only the
  auth stack is tested here. A host with the auth rules and no account rule
  counts failures and does not refuse an already-locked user
- **whether the ordering is right.** The `preauth` line must precede
  `pam_unix.so` and `authfail` must follow it. Verifying that means simulating
  the stack, which this module deliberately does not do
- **the effective threshold when it is set nowhere.** The module's own default
  applies; the finding says so rather than naming a number
- **whether accounts are currently locked.** That is `/var/run/faillock` state,
  not configuration

## 7. Known false positives

A host where authentication is delegated to a directory service that enforces
lockout centrally. The local stack genuinely does not count failures; the
control exists elsewhere. Suppress with the reasoning recorded.

## 8. Remediation

| | |
|---|---|
| Summary | Add `pam_faillock.so` to the auth and account stacks; set thresholds in `/etc/security/faillock.conf`. |
| Effort | MEDIUM |
| Steps | Use `authselect enable-feature with-faillock` or `pam-auth-update` rather than editing by hand; editing directly needs **three** rules and the order is the whole of it — `preauth` before `pam_unix.so`, `[default=die] … authfail` immediately after, `account required` in the account stack; set `deny`, `unlock_time` and `fail_interval` in the file; decide deliberately about `even_deny_root`; **prefer a finite `unlock_time`**; test with a throwaway account and `faillock --user … --reset` |
| Commands | `grep -E 'pam_faillock|pam_tally' /etc/pam.d/*`, `faillock --user someuser` |
| **Caution** | **Required.** No `unlock_time` turns brute force into a DoS anybody can trigger against any account whose name they know. `even_deny_root` on a host with no console and no single-user boot can lock you out permanently. |
