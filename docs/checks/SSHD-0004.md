# SSHD-0004 — Accounts with empty passwords cannot log in over SSH

| Field | Value |
|---|---|
| **ID** | `SSHD-0004` |
| **Module** | SSHD |
| **Base severity** | CRITICAL |
| **Tags** | ssh, remote-access, authentication, credentials |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `PermitEmptyPasswords` is `no`.

## 2. Why it matters

`PermitEmptyPasswords yes` allows an account whose password field in
`/etc/shadow` is empty to authenticate over SSH by pressing return. No guessing,
no credential, no rate limit that matters.

This is the SSH-facing half of USERS-0003. That check reports which accounts have
an empty password field; this one reports whether the SSH server will accept it.
Either alone is survivable. **Both together is remote unauthenticated access**,
which is why this is the only CRITICAL check in the module: no other single
`sshd_config` value produces that outcome by itself.

## 3. Source of truth

| | |
|---|---|
| Source | `sshd_config` `PermitEmptyPasswords` |
| Daemon default when unset | **`no`** (OpenSSH 9.x) |
| Reference | `sshd_config(5)` |

## 4. Distribution variations

None. Every distribution either omits the keyword or sets it to `no`. A host
failing this has been configured that way deliberately — most often an appliance
image built for convenience, a container base image where a password was never
set, or a hardening script that inverted a value.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `no`, or absent (the default is secure) | — | that an empty password field is refused |
| FAIL | `yes` | CRITICAL | the file and line |
| FAIL | `no` globally, `yes` inside a Match block | HIGH | the Match criteria, quoted |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

Note the contrast with SSHD-0003: there the built-in default is insecure and an
absent keyword FAILs; here it is secure and an absent keyword PASSes. That is
why the default is a declared field on every check in this module rather than an
assumption baked into the plumbing.

## 6. Where this check cannot know

- **whether any account actually has an empty password.** USERS-0003 answers
  that, and the two findings together are the ones that matter. This check alone
  reports a door with no way to tell whether anything is behind it
- **`UsePAM`.** With PAM in the path, `pam_unix`'s `nullok` option governs empty
  passwords independently, and a host can refuse them at one layer and accept
  them at the other. The AUTH module will read that; this check does not

## 7. Known false positives

None known in production. A container image under test where every account is
password-less is the only common case, and the correct answer there is that the
image should not run sshd.

## 8. Remediation

| | |
|---|---|
| Summary | Set `PermitEmptyPasswords no`, and fix the accounts that made it reachable. |
| Effort | LOW |
| Steps | set the keyword (or delete the line — the default is `no`); find empty-password accounts with `awk`; set or lock each; reload; **check whether the door was used** |
| Commands | `sshd -T \| grep -i permitemptypasswords`, `awk -F: '$2 == "" {print $1}' /etc/shadow` |
| **Caution** | **Required.** A service authenticating as an empty-password account will stop. That is correct, but find out what breaks before an outage tells you — and treat any account that was reachable this way as potentially compromised, not merely misconfigured. |
