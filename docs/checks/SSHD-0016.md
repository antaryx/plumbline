# SSHD-0016 — Unauthenticated connections are closed promptly

| Field | Value |
|---|---|
| **ID** | `SSHD-0016` |
| **Module** | SSHD |
| **Base severity** | LOW |
| **Tags** | ssh, remote-access, availability, attack-surface |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `LoginGraceTime` is greater than 0 and at most **60
seconds**.

## 2. Why it matters

`LoginGraceTime` is how long sshd holds a connection open before the client has
authenticated. Every such connection occupies one of the slots `MaxStartups`
allows and runs a pre-authentication process.

The default of 120 seconds lets an attacker hold the listener's unauthenticated
capacity with a trickle of connections that never complete — the slow-loris shape
applied to SSH. Sixty seconds or less halves the cost of holding a slot without
inconveniencing anyone: an interactive login taking more than a minute to
authenticate has a different problem.

The wider reason to care is that pre-authentication code is the most exposed code
in the daemon. It is what CVE-2024-6387 (regreSSHion) reached, and that
vulnerability was triggered specifically by **letting the grace timer expire** —
on a vulnerable host a shorter grace time raised the cost of the attack because
each attempt had to be repeated more often. Shortening the window does not fix
such bugs; it reduces how long an unauthenticated peer gets to work with the code
that contains them.

**0 disables the timeout** rather than tightening it: the connection is held
until the client goes away. It is the worst value, not the strictest, and a naive
`n <= 60` rule would have reported it as a pass.

## 3. Source of truth

| | |
|---|---|
| Source | `sshd_config` `LoginGraceTime` |
| Daemon default when unset | **`120`** seconds (OpenSSH 9.x) |
| Reference | `sshd_config(5)` |

Accepts sshd's TIME FORMAT: a bare number of seconds, or count/unit pairs such as
`2m` or `1h30m`. A parser reading `2m` as the integer 2 would report a two-minute
grace period as two seconds — a PASS for exactly the configuration this check
exists to find — so the check parses the format properly.

## 4. Distribution variations

None. No mainstream distribution changes the default.

**Not permitted inside a `Match` block.**

## 6. Where this check cannot know

- **`MaxStartups`**, which is the other half of the same calculation: the grace
  time and the connection limit together decide how cheaply the listener can be
  saturated. This module does not yet read it
- **the sshd version**, so it cannot say whether this host is actually exposed to
  CVE-2024-6387. That is a vulnerability-feed question
- **whether anything upstream rate-limits port 22**, which changes the exposure
  substantially

## 7. Known false positives

Authentication involving a hardware token, a push notification or a slow
directory lookup can legitimately take a while. Sixty seconds is comfortable for
all three; a site with an unusually slow second factor has a real case.

## 8. Remediation

| | |
|---|---|
| Summary | Set `LoginGraceTime` to 60 seconds or less. |
| Effort | LOW |
| Steps | set `LoginGraceTime 60`; **never set it to 0**; review `MaxStartups` at the same time; reload |
| Commands | `sshd -T \| grep -Ei 'logingracetime\|maxstartups'` |
| **Caution** | **Required.** Going much below 60 will start rejecting real logins during a directory outage or a slow second factor. |
