# SSHD-0009 — sshd logging is detailed enough to reconstruct access

| Field | Value |
|---|---|
| **ID** | `SSHD-0009` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, logging, forensics, attribution |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `LogLevel` is `INFO` or `VERBOSE`.

## 2. Why it matters

The authentication log is where an SSH compromise is found, and it is the only
place a successful login leaves a durable record.

At `ERROR` or below, sshd logs faults of the daemon but not the outcome of
authentication attempts: **successful logins produce nothing**. An investigation
into "who was on this host last Tuesday" has no source to consult, and the
absence is invisible until the moment it matters, at which point it cannot be
fixed retroactively.

`VERBOSE` adds the **fingerprint of the public key that authenticated**. That is
the difference between knowing somebody logged in as `deploy` and knowing which
of the eleven keys in that account's `authorized_keys` did it. On any host where
more than one key opens an account, `VERBOSE` is what makes key-based logins
attributable at all.

`DEBUG` and `DEBUG1`-`3` fail from the other direction. `sshd_config(5)` states
that logging at DEBUG "violates the privacy of users and is not recommended";
the volume can also roll a log file before an investigator reaches it. This is
reported at LOW — it is a privacy and retention problem rather than an absence of
evidence.

## 4. Distribution variations

None. Every mainstream distribution leaves the default or sets `INFO` explicitly.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `VERBOSE` | — | that key fingerprints are recorded |
| PASS | `INFO`, or absent | — | what `VERBOSE` would additionally record |
| FAIL | `QUIET`, `FATAL`, `ERROR` | MEDIUM | that successful logins produce no record |
| FAIL | `DEBUG`, `DEBUG1`-`3` | **LOW** | the privacy warning from `sshd_config(5)` |
| FAIL | acceptable globally, lower inside a Match block | LOW | the Match criteria, quoted |
| UNKNOWN | value is none of the accepted levels | `unparseable_source` | the accepted levels |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether the log is collected anywhere.** A local authentication log is
  deleted by whoever compromises the host; forwarding it to a collector is what
  makes it evidence. The LOGGING module (WP-20) covers that side
- **whether the log is being read.** A perfect log nobody alerts on has the same
  incident-response value as no log
- **retention.** `VERBOSE` on a busy bastion can roll a log file faster than the
  window an investigation needs

## 7. Known false positives

A host deliberately running at `DEBUG` while a specific fault is diagnosed is a
correct temporary state. The finding is still worth having: debug logging left on
after the investigation is the common failure, and it is what this check catches.

## 8. Remediation

| | |
|---|---|
| Summary | Set `LogLevel VERBOSE`, and confirm the log is actually being collected. |
| Effort | LOW |
| Steps | set the keyword; verify fingerprints appear after a key login; confirm the log leaves the host; if the level was DEBUG, review and rotate the existing files before leaving them in place; reload |
| Commands | `sshd -T \| grep -i loglevel`, `journalctl -u sshd -n 50` |
| **Caution** | **Required.** `VERBOSE` increases log volume noticeably on a busy bastion. Check retention and disk headroom first, or the first symptom will be a full filesystem rather than a better audit trail. |
