# AUTH-0005 — Passwords are hashed with a strong algorithm

| Field | Value |
|---|---|
| **ID** | `AUTH-0005` |
| **Module** | AUTH |
| **Base severity** | HIGH |
| **Tags** | auth, pam, password, hashing, credentials |
| **Facts required** | `auth.pam` |
| **Since catalog** | 10 |
| **Platforms** | Linux, PAM hosts only |

## 1. What is tested

The `pam_unix.so` rule in the **password** stack names `yescrypt`,
`gost_yescrypt`, `sha512` or `blowfish`, and does not name `md5`, `bigcrypt` or
`sha256`.

## 2. The hash decides what a stolen `/etc/shadow` is worth

It has no effect on anything an attacker does before that point and complete
effect afterwards, which is why it is worth getting right on a host where
nothing has gone wrong yet.

The difference is arithmetic:

| Algorithm | Why it is where it is |
|---|---|
| `yescrypt` | **memory-hard** — needs RAM per guess as well as cycles, which defeats the GPU rather than inconveniencing it. Current default on Debian and Fedora |
| `sha512` | 5000 rounds by default: four orders of magnitude slower than MD5, which moves a wordlist attack from hours into an unattractive amount of time |
| `blowfish` | bcrypt; tunable cost, likewise acceptable |
| `md5` | crypt's `$1$`. **Fast is the whole problem** — a commodity GPU tries it billions of times a second |
| `bigcrypt`, DES crypt | see below |

**DES crypt is worse than slow-versus-fast.** It uses the **first eight
characters of the password and discards the rest** — so a twenty-character
passphrase on such a host is an eight-character password, AUTH-0002's length
requirement is decoration, and the account is brute-forceable regardless of what
the user chose.

`sha256` is listed as weak here not because SHA-256 is broken but because
`sha512` is available everywhere `sha256` is, at the same cost, with a larger
margin. There is no host on which choosing it is the better answer.

## 3. The policy and the file are different questions

The algorithm applies **when a password is set**, not retroactively. Changing
it leaves every existing hash exactly as weak as it was.

- **This check** reports the policy — what the next password will be hashed
  with.
- **USERS-0006** reports what is actually in `/etc/shadow` — what an attacker
  steals today.

Both are needed and neither substitutes for the other. A host can pass this
check with a file full of MD5 hashes set years ago, which is why the
remediation's fourth step is the rotation rather than the edit.

## 4. No algorithm argument at all is UNKNOWN

Where `pam_unix.so` is present in the password stack with no algorithm
argument, the effective value comes from `ENCRYPT_METHOD` in `/etc/login.defs`
on some distributions and from libcrypt's compiled-in default on others —
neither of which this check reads, and both of which have changed between
releases.

Naming either answer from here would be a guess. In practice both mainstream
families state it explicitly (`sha512` on Red Hat, `yescrypt` on Debian), so
this branch fires only on genuinely unusual hosts, and the finding says that
naming it explicitly removes the ambiguity as well as the doubt.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | a strong algorithm is named | — | which, and **that the file is USERS-0006's question** |
| FAIL | a weak algorithm is named | HIGH | which, the file and line, the arithmetic, and that changing it is not retroactive |
| UNKNOWN | `pam_unix.so` present, no algorithm argument | `fact_unavailable` | that the value comes from `login.defs` or the libcrypt build |
| UNKNOWN | no `pam_unix.so` in the password stack | `fact_unavailable` | that either another module stores passwords, or the stack could not set one at all |
| NOT_APPLICABLE | no `/etc/pam.d` | — | that another mechanism authenticates here |
| UNKNOWN | `/etc/pam.d` unreadable, or an include unresolvable | `insufficient_privileges` / `ambiguous_system_state` | which |

## 6. Where this check cannot know

- **what is already in `/etc/shadow`.** USERS-0006
- **`ENCRYPT_METHOD` in `/etc/login.defs`.** `useradd` and `chpasswd` read that
  file rather than the PAM stack, so the two can disagree and an account's hash
  then depends on which tool created it. The remediation says to align them;
  this check does not read `login.defs`
- **the round count.** `rounds=` on the pam_unix line raises SHA-512's cost;
  not tested, because the default is already adequate and a wrong number here
  would fire on defensible configurations
- **whether libcrypt supports the named algorithm.** Setting `yescrypt` on a
  host whose libcrypt does not implement it makes password changes fail, and
  the file looks correct

## 7. Known false positives

A host that must interoperate with an old NIS or NFS-shared `/etc/shadow` where
the algorithm is fixed by the oldest participant. Real, rare, and worth
suppressing with the reasoning recorded.

## 8. Remediation

| | |
|---|---|
| Summary | Set `yescrypt` or `sha512` on the `pam_unix.so` password rule, then rotate the passwords hashed the old way. |
| Effort | MEDIUM |
| Steps | Choose what the distribution's libcrypt supports — **`yescrypt` on a host that lacks it makes every password change fail**; change it through `authselect` or `pam-auth-update`; set `ENCRYPT_METHOD` in `/etc/login.defs` to match, since `useradd` reads that instead; **rotate the existing passwords**, which is the step that actually changes what a stolen `/etc/shadow` is worth; confirm from a hash you just set — `$y$` yescrypt, `$6$` SHA-512, `$1$` MD5, no prefix DES |
| Commands | `grep -E 'pam_unix.so' /etc/pam.d/* \| grep password`, `grep ENCRYPT_METHOD /etc/login.defs`, `awk -F: '{print $1, substr($2,1,4)}' /etc/shadow` |
| **Caution** | **Required.** An unsupported algorithm makes every password change fail, and the failure appears the next time somebody runs `passwd` rather than when you save the file. Change a throwaway account's password immediately after the edit, while a root session is still open. |
