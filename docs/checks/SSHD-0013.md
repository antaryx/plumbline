# SSHD-0013 — Per-user .rhosts and .shosts files are ignored

| Field | Value |
|---|---|
| **ID** | `SSHD-0013` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, authentication, legacy |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `IgnoreRhosts` is `yes`.

## 2. Why it matters

`~/.rhosts` and `~/.shosts` are the BSD r-command trust files: a line naming a
host and a user says "let that user in from that host without a credential". The
trust is asserted by the client's hostname, which is exactly the thing an
attacker on the network controls.

The keyword only takes effect where host-based authentication is enabled
(SSHD-0014), so on most hosts this is defence in depth rather than an active
exposure. The two settings are frequently changed together by the same legacy
migration, though, and a host that has turned one on has usually turned the other
on too.

## 4. Distribution variations

None. A host failing this has been configured to honour the files deliberately,
which is worth knowing on its own.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `yes`, or absent (the default is secure) | — | that the files are not consulted |
| FAIL | `no` | MEDIUM | that a writable home directory can grant remote access |
| FAIL | `yes` globally, `no` inside a Match block | LOW | the Match criteria, quoted |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether host-based authentication is on.** Without it the setting has no
  effect. SSHD-0014 reports that separately, and the two findings together are
  what matters
- **whether any `.rhosts` file exists.** The files themselves are on disk, and
  reading arbitrary home directories is filesystem-walker territory rather than
  this module's
- **`IgnoreUserKnownHosts`**, the related keyword governing host-key trust, which
  this module does not yet read

## 7. Known false positives

None in practice. A legacy application still relying on r-command trust is a
standing unauthenticated-access path, not a false positive.

## 8. Remediation

| | |
|---|---|
| Summary | Set `IgnoreRhosts yes` and remove the trust files already on disk. |
| Effort | LOW |
| Steps | set the keyword (or delete the line — the default is `yes`); find existing files with `find`; **read each before deleting**, since its contents record who was trusted; confirm `HostbasedAuthentication no`; reload |
| Commands | `sshd -T \| grep -i ignorerhosts`, `find /home /root -maxdepth 2 \( -name .rhosts -o -name .shosts \)` |
| **Caution** | **Required.** A legacy application relying on r-command trust will stop authenticating. Those are rare in 2026 and each is a standing exposure, so find out what breaks rather than leaving the setting in place. |
