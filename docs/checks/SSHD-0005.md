# SSHD-0005 — X11 forwarding is disabled

| Field | Value |
|---|---|
| **ID** | `SSHD-0005` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, attack-surface, lateral-movement |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `X11Forwarding` is `no`.

## 2. Why it matters

X11 has no meaningful isolation between clients. A program connected to an X
display can read every keystroke sent to any other window on that display, take
screenshots of it, and inject synthetic input into it. That is the protocol
working as designed for a 1984 model of a trusted local network.

X11 forwarding extends that display across an SSH connection, so a compromise of
the server becomes a keylogger on the administrator's desktop. `ForwardX11Trusted`
makes this explicit; without it the X11 SECURITY extension restricts some
operations, but OpenSSH's own manual warns against relying on it.

## 4. Distribution variations

**Debian and Ubuntu ship `X11Forwarding yes` in their packaged `sshd_config`.**
This check therefore reports a finding on a stock installation of either, which
is the most common reason it appears. RHEL-family packages leave it at the
upstream default.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `no`, or absent (the default is secure) | — | that no session can reach a client's display |
| FAIL | `yes` | MEDIUM | the file and line, and the keylogging consequence |
| FAIL | `no` globally, `yes` inside a Match block | LOW | the Match criteria, quoted |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether any X server is reachable.** On a host whose users all connect from
  Windows terminals with no X server, the setting is inert. The check reports the
  offer, not its use
- **client-side `ForwardX11` settings**, which decide whether the offer is taken
  up. A server offering forwarding to clients that never request it is exposed
  only in principle
- **`X11UseLocalhost`**, which bounds where the forwarded display listens and is
  a related but separate control this module does not yet read

## 7. Known false positives

Administrators who run graphical installers or vendor consoles over SSH depend on
this, and on such hosts the finding is a statement of a real trade-off rather
than a defect. Scoping it to a `Match` block for the accounts that need it is the
narrower answer; Plumbline reports that as a conditional FAIL, which is the
honest reading — the capability exists for a named set of users.

## 8. Remediation

| | |
|---|---|
| Summary | Set `X11Forwarding no`; use a browser or a purpose-built remote desktop where a GUI is genuinely needed. |
| Effort | LOW |
| Steps | check the auth log for forwarding requests first; set the keyword (on Debian/Ubuntu the packaged line must be **changed**, not removed); scope with `Match` where a few users need it; `sshd -t` then reload |
| Commands | `sshd -T \| grep -i x11forwarding` |
| **Caution** | **Required.** Graphical tools stop working with no error more helpful than "cannot open display". Establish the replacement path before the change. |
