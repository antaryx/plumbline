# SSHD-0017 — A pre-authentication warning banner is presented

| Field | Value |
|---|---|
| **ID** | `SSHD-0017` |
| **Module** | SSHD |
| **Base severity** | LOW |
| **Tags** | ssh, compliance, policy |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

`Banner` is set to something other than `none`.

## 2. Why it matters

**This check is legal rather than technical, and it is written to say so.** A
banner stops no attacker and closes no exposure.

Its purpose is evidentiary. Several legal regimes — and most organisational
computer-use policies — distinguish between a system that announced its access
conditions and one that did not, and the announcement has to precede
authentication to be relied on. Where an organisation intends to be able to act
on unauthorised access, this is the mechanism that records the intent.

Two practical notes. The banner **must not describe the host**: version numbers,
hostnames, roles and contact details in a pre-authentication banner are
reconnaissance handed to anyone who connects, and the file is world-readable to
the internet by construction. And `Banner` is not `MOTD`, which is displayed
*after* authentication and therefore says nothing to anyone who failed to
authenticate.

## 4. Distribution variations

None ship a banner. Government and regulated builds commonly point at
`/etc/issue.net`.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | any value other than `none` | — | the path, **and that the file itself was not read** |
| FAIL | `none` | LOW | that the banner is explicitly disabled |
| FAIL | absent | LOW | that the built-in default is `none` |
| FAIL | set globally, `none` inside a Match block | INFO | the Match criteria, quoted |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether the file exists.** Plumbline does not read operator-named paths out
  of a directive (ADR-0011), and sshd **fails open** here: a `Banner` pointing at
  a missing file logs and continues, presenting nothing. A PASS therefore means
  the directive is set, not that a banner is shown, and the detail says so
- **what the banner says.** Whether the wording carries the legal effect intended,
  and whether it leaks host details, are both outside what a scanner can judge
- **`DebianBanner`**, which controls the OS identification appended to the SSH
  version string and is a different disclosure

## 7. Known false positives

An organisation that has deliberately decided a banner is unnecessary should
suppress this with that decision recorded — which is more useful than the banner
would have been.

## 8. Remediation

| | |
|---|---|
| Summary | Write a banner file containing your organisation's access notice and point `Banner` at it. |
| Effort | LOW |
| Steps | **get the wording from whoever owns it** — legal or security, not the person editing `sshd_config`; write it to `/etc/issue.net`; set the keyword; check the file names no hostname, version, role or contact; verify with `ssh -o PreferredAuthentications=none` |
| Commands | `sshd -T \| grep -i banner`, `ssh -o PreferredAuthentications=none <host>` |
| **Caution** | **Required.** Automated clients that parse SSH output — older scripted transfers, some monitoring probes — can be confused by unexpected banner text. Test against the automation that talks to this host, not only from an interactive terminal. |
