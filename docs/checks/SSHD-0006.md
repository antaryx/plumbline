# SSHD-0006 — Authentication attempts per connection are limited

| Field | Value |
|---|---|
| **ID** | `SSHD-0006` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, authentication, logging |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `MaxAuthTries` is between 1 and **4** inclusive.

## 2. Why it matters

`MaxAuthTries` bounds authentication attempts on a single TCP connection. It does
**not** limit how many connections an attacker may open, so it is not by itself a
defence against password guessing — `pam_faillock` and a network rate limit are
what do that. Any hardening guide presenting it as brute-force protection is
overselling it.

What it does control is the cost per connection and, less obviously, **what gets
logged**. sshd writes a failure to the authentication log only once a connection
has used more than *half* of `MaxAuthTries`. At the default of 6, the first three
attempts of every connection produce no log line at all — a meaningful blind spot
for anything watching that log for brute-force patterns. At 4, the third attempt
becomes visible.

0 is treated as a misconfiguration rather than maximum strictness: sshd refuses
every authentication at 0, which is a denial of service, and a bare `n <= 4` rule
would have reported it as the best possible value.

## 6. Where this check cannot know

- **whether a real lockout mechanism exists.** `pam_faillock` configuration is an
  AUTH-module fact this build does not collect, so a host with a perfect lockout
  policy and `MaxAuthTries 6` still fails here
- **how many keys clients offer.** Each key a client presents consumes one
  attempt, so a low limit can disconnect a user with several keys loaded before
  the right one is reached. That presents as an intermittent "Too many
  authentication failures" and is easy to misattribute to the server

## 7. Known false positives

A host whose users routinely have five or more keys in their agent will see real
login failures at 4. The correct fix is `IdentitiesOnly yes` on the client rather
than raising the server limit, but a site that cannot change client configuration
has a genuine reason to suppress this.

## 8. Remediation

| | |
|---|---|
| Summary | Set `MaxAuthTries 4` or lower, and add a real lockout mechanism alongside it. |
| Effort | LOW |
| Steps | set the keyword; configure `pam_faillock` and a firewall rate limit — this setting is not brute-force protection; check whether users have many keys loaded; `sshd -t` then reload |
| Commands | `sshd -T \| grep -i maxauthtries` |
| **Caution** | **Required.** Users with many keys in their agent can be disconnected before the correct key is offered. Warn them to set `IdentitiesOnly`, or raise the limit slightly rather than leaving it at the default. |
