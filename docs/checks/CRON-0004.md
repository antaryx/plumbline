# CRON-0004 — The cron access-control files are owned by root and writable only by root

| Field | Value |
|---|---|
| **ID** | `CRON-0004` |
| **Module** | CRON |
| **Base severity** | MEDIUM |
| **Tags** | cron, access-control, file-permissions |
| **Facts required** | `cron.files` |
| **Since catalog** | 7 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

Whichever of `/etc/cron.allow` and `/etc/cron.deny` exists is owned by uid 0 /
gid 0 and grants write permission to neither group nor other.

## 2. Why it matters

An access-control file that the accounts it governs can write is not an
access-control file. A writable `cron.allow` lets any user append their own name
and schedule jobs; a writable `cron.deny` lets them delete the line keeping them
out. Either way the restriction CRON-0003 reports as being in force is not in
force, and nothing about the configuration looks wrong — the mechanism is
present, correctly named, and doing nothing.

**This is why CRON-0003 and this check are separate.** The first asks which
mechanism governs cron access; this one asks whether that mechanism is beyond
the reach of the people it restricts. A host can pass one and fail the other,
and that combination — an allow list anyone may edit — is worse than having no
allow list at all, because it produces a report saying access is restricted.

Read permission is not part of this check. Both files are world-readable by
default on most distributions and that is harmless: knowing who may schedule
jobs is not itself an exposure.

## 4. Distribution variations

Debian and Ubuntu ship neither file, so this check is NOT_APPLICABLE on a stock
install of either. RHEL and Fedora ship `/etc/cron.deny` as `root:root` 0600,
which passes.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | every file present is root-owned and not group/other writable | — | which files were examined |
| FAIL | a file's owner is not uid 0 / gid 0 | MEDIUM | the path, uid and gid |
| FAIL | a file's mode grants group or other write | MEDIUM | the path and the octal mode |
| NOT_APPLICABLE | neither file exists | — | that CRON-0003 reports the absence itself |
| NOT_APPLICABLE | no system cron on this host | — | — |
| UNKNOWN | no violation found but a path could not be stat'ed | `insufficient_privileges` | which paths were unknowable |

The neither-file case is NOT_APPLICABLE rather than FAIL on purpose: the absence
is a real finding, and it is CRON-0003's. Reporting it here as well would put
the same defect in front of the reader twice under two different names, and
they would fix one and see the other still open.

## 6. Where this check cannot know

- **who is on the list**, or whether an entry was added while the file was
  writable. No contents are read
- **whether the exposure was used.** A file that was writable yesterday and is
  correct today passes; the crontab spool is where the evidence would be, and
  it is not collected in WP-19
- **the parent directory's mode.** `/etc` being writable would let an attacker
  replace either file wholesale regardless of the file's own mode. That is a
  filesystem-walker question

## 7. Known false positives

None known.

## 8. Remediation

| | |
|---|---|
| Summary | Restore root ownership and remove group and other write permission from the access-control files. |
| Effort | LOW |
| Steps | **read the file first** and check every name against who is supposed to be there; `chown root:root` and `chmod 600`; cross-check the crontab spool, since a name added to `cron.allow` is only useful alongside a crontab; consider removing `cron.deny` entirely if `cron.allow` exists, because cron ignores it |
| Commands | `stat -c '%n %a %U:%G' /etc/cron.allow /etc/cron.deny`, `chown root:root /etc/cron.allow && chmod 600 /etc/cron.allow` |
| **Caution** | **Required.** Changing the mode does not undo anything added while the file was writable. Read the contents and the crontab spool before fixing the permissions — fixing them first removes the thing that would tell you whether the exposure was used. |
