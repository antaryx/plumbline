# AUTH-0006 — Recent passwords cannot be reused

| Field | Value |
|---|---|
| **ID** | `AUTH-0006` |
| **Module** | AUTH |
| **Base severity** | LOW |
| **Tags** | auth, pam, password, history |
| **Facts required** | `auth.pam` |
| **Since catalog** | 10 |
| **Platforms** | Linux, PAM hosts only |

## 1. What is tested

A `remember=` argument of at least **5** on `pam_pwhistory.so` or
`pam_unix.so` in the **password** stack.

## 2. History exists to make expiry mean something

Where a host requires a change every ninety days and remembers nothing, the
ordinary response is to change the password to the same one — or to cycle two —
and the expiry policy becomes a recurring inconvenience that produces no
security at all. Worse, it produces the predictable variants an attacker's rule
engine generates first: the same word with an incrementing digit is the single
most common pattern in every leaked corpus.

It matters most **after a compromise**. When a credential is known to have
leaked and every affected account is forced to change, history is what stops
the change being a no-op — and the account most likely to be reset to its
previous password is exactly the one whose previous password an attacker
already has.

## 3. Why this is LOW, and it is a disagreement rather than a hedge

| | |
|---|---|
| CIS, DISA STIG | remember at least **5** |
| NIST SP 800-63B §5.1.1.2 | recommends **against routine expiry** — forced rotation drives users toward predictable transformations; change on evidence of compromise instead |

Password history is a control that mainly exists to prop up rotation. On a host
that does not expire passwords — which is what NIST recommends — it is close to
redundant.

The finding is reported so the decision is visible, at a severity that says it
is not the thing to fix first. This is the same treatment USERS-0010 gives the
maximum-age question, which carries the other half of the same disagreement.

## 4. Two modules keep the history

`pam_pwhistory.so` is the dedicated one. `pam_unix.so` takes the same
`remember` argument and keeps the history itself, which is what Red Hat's stack
has historically used. Looking only for `pam_pwhistory` would report no history
on a host that has one, so both are searched and the largest `remember` value
found is the effective one.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `remember` ≥ 5 | — | the value and where it was read |
| FAIL | `remember` present but < 5 | LOW | the value, and that a short history is satisfied by cycling a small set |
| FAIL | no history module or argument | LOW | that a forced change may be satisfied by the password being replaced, **and the NIST/CIS disagreement** |
| NOT_APPLICABLE | no `/etc/pam.d` | — | that another mechanism authenticates here |
| UNKNOWN | `/etc/pam.d` unreadable, or an include unresolvable | `insufficient_privileges` / `ambiguous_system_state` | which |

## 6. Where this check cannot know

- **whether passwords expire at all.** USERS-0009 and USERS-0010 answer that.
  Without expiry this control has little to do
- **the mode of `/etc/security/opasswd`.** That file holds previous password
  *hashes* and needs the same protection as `/etc/shadow`. A world-readable
  `opasswd` hands an attacker every password a user has ever had, which is a
  larger prize than the current one — and it is created by the module the first
  time a password changes, so it does not exist to be checked until after this
  control is enabled. The remediation says to check it; no check does yet
- **whether the history is populated.** A freshly enabled module remembers
  nothing until passwords start changing
- **`use_authtok` placement.** Without it the module prompts separately, which
  is a usability fault rather than a security one

## 7. Known false positives

A host that has deliberately adopted NIST SP 800-63B — no expiry, no
composition rules, no history. Suppress with the reasoning recorded; the
finding names the disagreement precisely so this is a decision rather than an
oversight.

## 8. Remediation

| | |
|---|---|
| Summary | Add `pam_pwhistory.so remember=5` to the password stack, above `pam_unix.so`. |
| Effort | LOW |
| Steps | **Decide whether you want this control at all** — if the host does not expire passwords, suppressing with that reasoning is a legitimate answer; add it via `authselect` or `pam-auth-update`; editing directly, the rule goes **above** `pam_unix.so`, because below it the password is already set; alternatively add `remember=5` to the existing `pam_unix.so` rule — one or the other, not both; **check `/etc/security/opasswd`'s mode after enabling**; test by changing a throwaway account's password and trying to change it back |
| Commands | `grep -E 'pam_pwhistory|remember=' /etc/pam.d/*`, `ls -l /etc/security/opasswd` |
| **Caution** | **Required.** `/etc/security/opasswd` holds previous password hashes and is created by the module at the first password change. If it ends up world-readable this control has handed an attacker every password each user has had rather than only the current one — check its mode after enabling, not before. |
