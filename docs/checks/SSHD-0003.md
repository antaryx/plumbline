# SSHD-0003 — Password authentication over SSH is disabled

| Field | Value |
|---|---|
| **ID** | `SSHD-0003` |
| **Module** | SSHD |
| **Base severity** | HIGH |
| **Tags** | ssh, remote-access, authentication, credentials |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `PasswordAuthentication` is `no`.

## 2. Why it matters

A password is a secret a person can be persuaded to type. Over SSH it is also a
secret an attacker can attempt from anywhere on the internet, at whatever rate
the server tolerates, against a username list that is largely guessable. Every
large-scale SSH compromise of the last two decades has run through this door.

Public-key authentication removes the class: the private key never leaves the
client, there is nothing to guess, and a stolen credential is a file an attacker
must first obtain rather than a string they can derive.

## 4. Distribution variations

Debian, Ubuntu and RHEL all ship the keyword explicitly as `yes`, so this check
reports a finding on a stock installation of every mainstream distribution. That
is correct rather than noisy.

Ubuntu cloud images add a drop-in under `/etc/ssh/sshd_config.d/` that sets it
to `no`; because `Include` is on line 1 of the main file, the drop-in wins. The
collector resolves includes in order, so Plumbline reports the effective value
rather than the one visible in `sshd_config`.

## 6. Where this check cannot know

- **`KbdInteractiveAuthentication`.** With `UsePAM yes`, PAM can still accept a
  password through keyboard-interactive even when `PasswordAuthentication no` is
  set. This check does not read that keyword, so a PASS here does not on its own
  prove passwords are refused. This is the most common reason the change appears
  not to take effect, and it is called out in the remediation
- **whether any account has a usable password at all.** USERS-0003 and USERS-0004
  answer that; a host where every account is key-only loses nothing by this
  setting being wrong, and a host where every account has a weak password loses
  everything
- **what the running daemon is using.** Plumbline parses files; `sshd -T` is
  deferred (the v0.2 work plan (WP-18))

## 7. Known false positives

A bastion that deliberately accepts passwords behind an MFA PAM module is a real
architecture, and the finding is correct about the file while being wrong about
the risk. Suppress it with a justification naming the second factor.

## 8. Remediation

| | |
|---|---|
| Summary | Deploy keys for every account that needs SSH access, then set `PasswordAuthentication no`. |
| Effort | MEDIUM |
| Steps | establish key access and verify it in a separate session; list accounts relying on passwords; set the keyword; **also set `KbdInteractiveAuthentication no`**; `sshd -t` then reload |
| Commands | `sshd -t`, `sshd -T \| grep -Ei 'passwordauthentication\|kbdinteractive'` |
| **Caution** | **Required.** The change most likely to lock you out of a remote host. Verify key auth in a second independent session first, never reload from the session you would lose, and arrange console access if the host has none. |
