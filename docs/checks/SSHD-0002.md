# SSHD-0002 — Root login over SSH is disabled

**Status:** implemented. This is the worked reference; the implementation is
`internal/catalog/checks/sshd/sshd0002.go`.

| Field | Value |
|---|---|
| **ID** | `SSHD-0002` |
| **Module** | `SSHD` |
| **Base severity** | HIGH |
| **Tags** | `ssh`, `remote-access`, `accountability` |
| **Facts required** | `sshd.config` (v1) |
| **Since catalog** | 1 |
| **Platforms** | Linux (all) |

## 1. What is tested

The effective global value of `PermitRootLogin` in the sshd server
configuration is `no`.

## 2. Why it matters

Direct root login removes the accountability sudo provides — every action is
attributed to "root" rather than to a person — and it hands remote attackers a
username guaranteed to exist on every system, which makes credential attacks
meaningfully cheaper. `PermitRootLogin no` forces an administrator to
authenticate as themselves and then escalate, leaving an audit trail.

## 3. Source of truth

| | |
|---|---|
| Source | `/etc/ssh/sshd_config` and every file reached through `Include` |
| Daemon default when unset | `prohibit-password` (since OpenSSH 7.0, 2015) — key-based root login remains possible |
| Precedence | **First obtained value wins.** Later occurrences are ignored. |
| Scope | Directives after a `Match` line are conditional and do not set the global value |
| Reference | `sshd_config(5)`, `PermitRootLogin` |

The default matters: absence is neither "insecure" nor "fine". Treating absence
as FAIL-HIGH would be a false positive; treating it as PASS would be false
assurance. It is a genuine MEDIUM.

## 4. Distribution variations

| Distro | Variation | Verified |
|---|---|---|
| Ubuntu 22.04 / 24.04 | Ships `Include /etc/ssh/sshd_config.d/*.conf` on line 1, so cloud-init drop-ins take precedence over the main file | Yes — fixture `sshd-include` |
| Debian 12 / 13 | Same include pattern | Fixture |
| RHEL / Rocky 9 | Includes `/etc/ssh/sshd_config.d/*.conf`; crypto-policies may add files | Not yet |
| Alpine | No include by default | Not yet |
| Arch | No include by default; upstream defaults | Not yet |

## 5. Verdict table

| Result | Condition | Severity | Detail states |
|---|---|---|---|
| PASS | Effective value is `no` | HIGH (unused) | Value and that root login is refused |
| FAIL | Effective value is `yes` | HIGH | Value, file, line, that password login is possible |
| FAIL | Effective value is `prohibit-password`, `without-password`, or `forced-commands-only` | MEDIUM | Value, file, line, that key-based root login remains and actions are not attributable |
| FAIL | Keyword absent, no unresolved includes | MEDIUM | That the daemon default `prohibit-password` applies |
| NOT_APPLICABLE | No sshd configuration found | — | That the SSH server is not configured here |
| UNKNOWN | `sshd_config` unreadable | — | reason `insufficient_privileges` |
| UNKNOWN | Keyword absent **and** one or more includes unresolved | — | reason `ambiguous_system_state`, naming the unresolved patterns |
| UNKNOWN | Value unrecognised | — | reason `unparseable_source`; sshd would refuse to start, so the running config differs |

## 6. Where this check cannot know

- The file exists but cannot be read (unprivileged run)
- An `Include` pattern matched nothing, or a matched file could not be read —
  the value may live in a file never seen. **This is the case a lesser tool
  gets wrong**, reporting the documented default with false confidence.
- The value is syntactically invalid, so the running daemon cannot be using
  this file
- The configuration read is not what the running daemon loaded (started with
  `-f`, or edited since start). Not detectable from files alone; `sshd -T`
  cross-checking is a v0.2 enhancement.

## 7. Known false positives

| Situation | Response |
|---|---|
| Bastion hosts intentionally permitting `forced-commands-only` for an automated backup path | Suppression with justification and expiry |
| Immutable-image hosts where the only access is a key-based root login by design | Suppression; the accountability argument still applies and should be recorded |

## 8. Remediation

| | |
|---|---|
| Summary | Set `PermitRootLogin` to `no` and reload sshd |
| Effort | LOW |
| Steps | 1. Confirm a non-root account can log in over SSH and escalate with sudo. 2. Verify it works **in a second, separate session** before continuing. 3. Set `PermitRootLogin no` in `sshd_config`, or in a drop-in if the distro uses `Include`. 4. `sshd -t`. 5. Reload; keep the existing session open until a new one is verified. |
| Commands | `sshd -t` · `systemctl reload sshd` |
| **Caution** | Applying this while your only access is a root SSH session will lock you out. Never reload sshd from the session you would lose. |

## 10. Fixtures

| Fixture | Scenario | Expected |
|---|---|---|
| `sshd-hardened` | Explicit `PermitRootLogin no` | PASS |
| `sshd-permit-yes` | Explicit `yes` | FAIL / HIGH |
| `sshd-default` | Keyword commented out | FAIL / MEDIUM |
| `sshd-include` | `no` in a drop-in included on line 1, `yes` later in the main file | PASS — precedence |
| `sshd-match-trap` | Global `yes`, `no` inside `Match Address` | FAIL / HIGH — Match is scoped |
| `sshd-absent` | No sshd configuration | NOT_APPLICABLE |
| `sshd-unreadable` | euid 1000, config unreadable | UNKNOWN / `insufficient_privileges` |
| `sshd-unresolved-include` | Include matches nothing, keyword absent | UNKNOWN / `ambiguous_system_state` |
| `sshd-bad-value` | `PermitRootLogin maybe` | UNKNOWN / `unparseable_source` |

Nine fixtures covering all five result states. This is the standard to aim at
for anything security-significant.
