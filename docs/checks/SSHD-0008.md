# SSHD-0008 — TCP forwarding is restricted

| Field | Value |
|---|---|
| **ID** | `SSHD-0008` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, network, lateral-movement |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `AllowTcpForwarding` is not one of the unrestricted values
`yes` or `all`.

## 2. Why it matters

TCP forwarding turns an SSH session into a general-purpose network tunnel. Any
user who can authenticate can reach any address this host can reach (`ssh -L`),
and can expose any port of this host's network to their own client (`ssh -R`).
**Neither requires a shell**: an account with `/usr/sbin/nologin` still forwards.

Network segmentation is usually the control that survives when everything else
has failed. A database in a private subnet, a management interface on a separate
VLAN, an internal API with no authentication because it is "not reachable" — all
of them are reachable from a workstation the moment one account on a host in that
subnet can forward. Egress filtering fails the same way in reverse.

| | |

| Source | `sshd_config` `AllowTcpForwarding` |
| Daemon default when unset | **`yes`** (OpenSSH 9.x) |
| Reference | `sshd_config(5)` |

## 4. Distribution variations

None in the default. `local` and `remote` have been accepted since OpenSSH 6.2.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `no` | — | that neither direction is available |
| PASS | `local` | — | that `-R` is refused and **`-L` remains available** |
| PASS | `remote` | — | that `-L` is refused and **`-R` remains available** |
| FAIL | `yes` or `all` | MEDIUM | that segmentation around this host does not constrain an authenticated user |
| FAIL | absent | MEDIUM | that the default is `yes`, and that a nologin shell does not prevent it |
| FAIL | restricted globally, unrestricted inside a Match block | LOW | the Match criteria, quoted |
| UNKNOWN | value is none of the five | `unparseable_source` | the five accepted values |
| NOT_APPLICABLE | no sshd configuration | — | — |

`local` and `remote` pass with the remaining direction named. Which one a host
needs is a question about its role that no scanner can answer, and reporting the
partial restriction as a failure would push operators toward `yes`.

## 6. Where this check cannot know

- **that this is not a boundary against a determined user.** Anyone who can
  execute code on the host can run their own tunnel. The setting removes the
  default and the accident, not the adversary who already has a shell
- **`PermitOpen` and `PermitListen`**, which narrow forwarding to named
  destinations and are the finer-grained answer this module does not yet read
- **`DisableForwarding`**, which turns off X11 and TCP forwarding together
- **`GatewayPorts`**, which decides whether a `-R` listener is reachable from
  outside the host

## 7. Known false positives

A bastion exists to forward. On one, `yes` is the intended configuration and the
finding is correct about the file and wrong about the design. Scope it to a
`Match Group` block for the accounts that need it, or suppress with a
justification.

## 8. Remediation

| | |
|---|---|
| Summary | Set `AllowTcpForwarding no`, or restrict it to the direction the host's role requires. |
| Effort | MEDIUM |
| Steps | establish what uses it — forwarding is invisible in most monitoring; set `no` on hosts with no tunnelling role; on a bastion scope it with `Match Group`; combine with `ForceCommand internal-sftp` for sftp-only accounts, since a shell restriction alone does not stop forwarding; reload |
| Commands | `sshd -T \| grep -i allowtcpforwarding` |
| **Caution** | **Required.** Database clients, CI runners and remote IDE sessions frequently tunnel through a host without anyone recording that they do. The failure surfaces on the client, far from the host you changed. |
