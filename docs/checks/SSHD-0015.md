# SSHD-0015 — Users cannot set arbitrary environment variables at login

| Field | Value |
|---|---|
| **ID** | `SSHD-0015` |
| **Module** | SSHD |
| **Base severity** | MEDIUM |
| **Tags** | ssh, remote-access, privilege |
| **Facts required** | `sshd.config` |
| **Since catalog** | 6 |
| **Platforms** | Linux, all distributions |

## 1. What is tested

The effective global `PermitUserEnvironment` is `no`.

## 2. Why it matters

`PermitUserEnvironment yes` makes sshd read `~/.ssh/environment` and the
`environment=` options in `~/.ssh/authorized_keys`, applying what it finds to the
session before any shell starts. A file the user can write therefore becomes the
environment of a process the system starts on their behalf.

`LD_PRELOAD` is the direct route: a user who can set it loads a library of their
choosing into every program run from that session, including anything the session
later escalates to. `PATH`, `LD_LIBRARY_PATH` and `BASH_ENV` are variations.

Where this matters most is exactly where the user was supposed to be
constrained — a forced-command key, a restricted shell, an sftp-only account.
Each of those confines what the user may **run**; none of them confines what the
user may **load into it**.

`sshd_config(5)` recommends leaving this at its default.

## 4. Distribution variations

None.

**Not permitted inside a `Match` block.** `sshd_config` restricts which keywords
may appear there and this is not one, so there is no conditional-override path
for this check.

## 5. Verdict table

| Result | Condition | Severity | Detail must state |
|---|---|---|---|
| PASS | `no`, or absent (the default is secure) | — | that the environment comes from the system |
| FAIL | `yes` | MEDIUM | the `LD_PRELOAD` consequence and the forced-command bypass |
| UNKNOWN | value is neither `yes` nor `no` | `unparseable_source` | that sshd would reject the file |
| UNKNOWN | absent and an `Include` did not resolve | `ambiguous_system_state` | which include failed |
| NOT_APPLICABLE | no sshd configuration | — | — |

## 6. Where this check cannot know

- **whether any `~/.ssh/environment` file exists**, or whether any
  `authorized_keys` line carries `environment=`. Those are on disk and are not
  read here, so a FAIL reports the capability rather than its use
- **`AcceptEnv` and `SetEnv`**, the administrator-controlled alternatives, which
  this module does not yet read. A host that has migrated to them correctly still
  needs this keyword set to `no`
- **`PermitUserRC`**, the related keyword governing `~/.ssh/rc`

## 7. Known false positives

Build agents and deployment keys sometimes set variables through
`authorized_keys`. The finding is correct — the mechanism is a privilege
boundary hole — and the migration is to `SetEnv` on the server side.

## 8. Remediation

| | |
|---|---|
| Summary | Set `PermitUserEnvironment no` and use `AcceptEnv` or `SetEnv` for variables that genuinely need to pass through. |
| Effort | LOW |
| Steps | find what relies on it in `~/.ssh/environment` and `authorized_keys`; set the keyword; name required variables explicitly with `AcceptEnv` or `SetEnv`; reload |
| Commands | `sshd -T \| grep -i permituserenvironment`, `ls /home/*/.ssh/environment 2>/dev/null` |
| **Caution** | **Required.** Automation setting variables through `authorized_keys` loses them **silently** — the session starts normally and the variable is simply absent. Check for the files before reloading rather than after the first failed job. |
